✗ Check out the new branch — in each repo
✗ VS Code loses open files and scroll positions
✗ Your AI session starts cold — re-brief it

With wksp
✓ Every task has its own checkout of every repo
✓ Both tasks live simultaneously, on their own branches
✓ One VS Code window per task, state intact
✓ Each task keeps its own AI session and work log

The primitive: git worktrees

Built into git since v2.5 — wksp makes them effortless across every repo in your project

One git database — many working directories — many branches
C:/demo/repos/api/ ← base clone, on main
acme/tasks/PROJ-1234/worktrees/api/ ← worktree, on feature/PROJ-1234
acme/tasks/PROJ-5678/worktrees/api/ ← worktree, on hotfix/PROJ-5678

# All three share one .git object database — you pay for files, not history
# And git enforces it: one branch, one working directory

git checkout feature/PROJ-1234
fatal: 'feature/PROJ-1234' is already used by worktree at '.../PROJ-1234/worktrees/api'
git solves the branch half. wksp does the bookkeeping: creating and naming worktrees across every repo at once, generating the VS Code workspace, handing every path to your AI tool, keeping the record of what the task was for, and tearing it all down when it merges.

Register your repos once

One-time setup per product area — under a minute

Terminal
wksp init acme
✓ acme/
✓ AGENTS.md (+ CLAUDE.md include)
✓ PLANNING.md · ORCHESTRATION.md

cd acme
wksp repo add C:/demo/repos/api
wksp repo add C:/demo/repos/web
wksp repo add C:/demo/repos/docs --shared
✓ 3 repos registered
🌿
Worktree default
Each task gets its own isolated branch checkout. The mode for repos you actually change.
📖
--shared
Reference material — docs, design systems, repos you don't own. Always the base folder, never branched.
🔌
--optional
Only one task ever needs it. Excluded by default, so it stops interrogating you on every create. Pull it in with wksp task repo.
A GitHub URL works too — wksp repo add https://github.com/org/repo clones it, then registers it.

What lands on disk

acme/
acme/

  ├── repos.txt             the universe of repos
  ├── AGENTS.md             conventions — shared with tasks
  ├── PLANNING.md           backlog, open decisions

  │       ├── WORKLOG.md        what was actually changed
  │       ├── acme--PROJ-1234.code-workspace

  │           ├── api/          feature/PROJ-1234
  │           └── web/          feature/PROJ-1234
  └── archived-tasks/        done work, context kept
📁
One folder per task
Everything for a ticket lives together. Open the .code-workspace and every repo is in the sidebar, on the right branch.
📝
Two levels of context
Project conventions plus task goals. Your AI reads both automatically — you never re-explain the architecture.
📦
Nothing is thrown away
Finished tasks move to archived-tasks/: worktrees gone, branch state and work log preserved. wksp task unarchive brings it back.

Closing out a merged task

wksp task finish — verify, archive, clean up, fast-forward

Terminal
wksp task finish PROJ-5678

Fetching base repos ...
✓ hotfix/PROJ-5678 merged — PR #128 (confirmed on GitHub)
Removing worktrees ...
✓ api ✓ web
✓ Deleted local branch hotfix/PROJ-5678
✓ api → main fast-forwarded
✓ Archived → archived-tasks/PROJ-5678
Why it asks GitHub. A squash- or rebase-merge rewrites your branch into a new commit, so the branch tip is never an ancestor of main — pure git ancestry reported "not merged" on every finish. It now checks ancestry first, and when that's inconclusive asks the forge about the actual PR. gh is entirely optional; without it, finish falls back to asking you.

What's new

The hub, headless delegation, and everything since v1
Live demo

The project root is the planning hub

wksp start with no task id — plan above your tasks, not inside one

FileWhat it holdsLoaded into a task session?
AGENTS.mdConventions genuinely shared with every task✓ yes
PLANNING.mdThe backlog, open decisions, research pointers✗ no
ORCHESTRATION.mdHub-only: delegation, PR review, stacked PRs, settings✗ no
WORKLOG.mdWhat was decided at project level, and why✗ no
That third column is the whole design. Only the instruction file is injected into a task session — so the backlog doesn't bloat every task's context, and a task-scoped agent isn't handed instructions on how to delegate work, spawn reviewers, or pick merge methods. Role confusion is the real cost; the tokens are the smaller half.

wksp runs headless

The change that makes hub-driven work possible at all

From a planning session at the root
wksp task create PROJ-4242 \
--goal "Add pagination to the sessions endpoint" \
--branch feature/PROJ-4242 --json

# no prompts · launches nothing · prints the task brief on stdout
{ "ok": true, "briefVersion": 1, "task": { … }, "repos": [ … ] }
The brief
Paths, per-repo branch and mode, where to log, what belongs in the hub instead. Re-print any time with wksp task brief <id>.
--goal is the contract
It lands in the task's AGENTS.md — the one line stating what this task is and isn't for.
Use create, not start
start partial-matches, so a new id that's a substring of an existing task silently resumes that one.
A task folder lives under the project root — so a session at the root can work inside a task from its brief exactly as if it had been launched there.

A new category: wksp's CLI never acts on these — the orchestrating agent reads them and follows them. On this project reviewLoop: always has caught a data-loss path, a silent no-op, and a safety guard that failed open — all with a green test suite.

Two more things worth knowing

Stacked PRs — guidance shipped product-wide
One reframe carries it: stacking constrains merge order, not build order. Decide by code overlap — disjoint areas get parallel tasks and independent PRs off main with no stack at all; overlapping regions get chained branches, because building them in parallel only defers the same conflicts to stack time. Every project's ORCHESTRATION.md now carries the mechanics.
It got a lot harder to hurt yourself
Teardown now refuses up front rather than half-removing a task while your shell sits inside it, and nothing is ever skipped in silence. wksp can no longer mistake your home directory for a project — the marker and the global config share a filename, and wksp delete could offer to delete ~. And path comparisons are canonicalised, which closed a guard that failed open on Windows short paths.

The one you're most likely to have hit: checking out a branch a colleague pushed since your last fetch used to die on fatal: invalid reference — wksp asked the server whether the branch existed, then handed git a name only resolvable locally. It fetches first now. And a setup run that stops part-way no longer discards the answers you already gave: re-running finishes the job.

Migrating

If you already have wksp projects

Two commands, then one habit to unlearn

In each existing project
wksp migrate --dry-run
# always look first — shows every change without writing
wksp migrate
✓ Project migrated to schema 7

Scaffolds the planning files, converts instruction files to AGENTS.md + include, and relocates the hub-only guidance. It only ever inserts — your prose is never rewritten, and a block you've edited is left in place and reported rather than replaced. wksp migrate --repair backfills anything a task is missing.

If your muscle memory says…Type this
wksp task PROJ-1234wksp start PROJ-1234

wksp task PROJ-1234 --to-shared apiwksp task repo PROJ-1234 api share
wksp repo /c/dev/apiwksp repo add /c/dev/api
