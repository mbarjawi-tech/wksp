🚨
Top concern: wksp task is doing seven jobs — it creates, opens, deletes, renames, archives, unarchives, and adjusts per-repo settings. This single command carries so much responsibility that none of it is discoverable.
⚠️
Second concern: wksp cleanup --stale <path> uses a mandatory flag as a positional argument, the only short flag in the entire tool (-r), and requires a path even when inside a project that knows all its repos.
ℹ️
What's working well: The three-concept hierarchy (Project → Repo → Task), the archive/restore system, the Claude session resume logic, and the per-task shared/excluded state are all well-designed. None of the proposed changes touch the core mechanics — they reshape the surface.
🔍 Role 1 — Critic
Critic

Everything that should be questioned: confusing flags, redundant features, poor defaults, missing functionality. Direct.

Command Design

1
Critical   wksp task is doing seven jobs
▼

--del, --rename, --archive, --unarchive, --to-shared, --to-worktree, --to-exclude are all flags on the same command that also creates and opens tasks. A user types wksp task PROJ-123 expecting to open a task and gets no warning that this same command also tears it down. The flags exist only to avoid creating new top-level commands, and it shows.

2
Critical   wksp cleanup --stale <path> is the worst-designed command
▼

The --stale flag is required — the command does nothing without it and errors. That makes it a mandatory argument disguised as an option. -r for recursive is the only short flag in the entire tool. The command can't scan the current project's repos automatically — you must pass a path explicitly even when inside a project that already knows all its repos.

3
High   wksp repo uses flags for actions that should be subcommands
▼

wksp repo /path --remove is backwards. Every other mutation in this tool is a verb: wksp delete, wksp cleanup, wksp init. Removing a repo should be wksp repo remove /path. There is also no wksp repo list — you have to open repos.txt manually to see what's registered.

4
High   --rename launches Claude after renaming
▼

wksp task PROJ-123 --rename PROJ-456 renames the folder and then opens Claude Code. If someone just wants to rename a task, they get Claude too. The rename is a filesystem operation; launching is a separate intent. These should not be coupled.

5
High   wksp delete asks for y to delete everything
▼

The confirmation is a y/N prompt. Given that it tears down all worktrees and deletes the entire project folder, typing the project name is the appropriate bar. This is the standard for destructive CLI operations (e.g. Heroku's heroku apps:destroy --confirm myapp).

6
Medium   wksp status only works inside a task directory
▼

wksp status PROJ-123 from the project root does not work. There is no way to inspect a task without cd-ing into it. The command should accept an optional task ID argument.

Flag Naming & Consistency

7
High   --del is inconsistent with wksp delete
▼

The project-level deletion command is wksp delete. The task-level deletion flag is --del. Same concept, different abbreviation, no reason for either choice. Every other long flag in this tool is spelled out in full: --shared, --remove, --global, --archive.

8
High   --to-shared, --to-worktree, --to-exclude are verbed wrong
▼

"to-X" sounds like a conversion target but reads as a preposition. The verbs are missing. --to-exclude is the strangest — "to exclude" is a verb phrase that does not fit the flag convention. These should describe the state to apply: --use-shared, --use-worktree, --exclude.

9
Medium   --shared collides with git terminology
▼

git clone --shared means share the object store between repos. In wksp, --shared means "never create a worktree — always use the repo's original path." A developer coming from git maps --shared to a completely different concept. A clearer name would be --no-worktree or --in-place. (Deferred — breaks repos.txt format.)

10
Medium   config set errors outside a project instead of defaulting to global
▼

Running wksp config set reposRoot /path outside a project gives: "Error: not inside a wksp project — use --global to set a global value." Most users setting reposRoot have no project yet. The command should default to global with a note, not error.

Missing Features

11
High   No wksp --version
▼

Standard CLI expectation. Missing entirely. Every developer's first debugging instinct is to check the version. Not having it is a broken expectation.

12
High   No per-command --help
▼

wksp task --help does not print task usage — it runs task with ['--help'] as args, which either fails or behaves unexpectedly. Every command should intercept --help in its own run() and print usage with examples.

13
Medium   wksp list gives no indication that archived tasks exist
▼

If you archived PROJ-123 and run wksp list, you see nothing for it. No indication that anything is archived. The output footer should read: "N archived task(s) — run wksp list --archived to see them."

14
Low   autoResume config key and WKSP_DEBUG env var are invisible
▼

autoResume is read in task.js and affects behavior, but appears nowhere in help output. WKSP_DEBUG enables stack traces in the error handler but is not documented anywhere visible. Both belong in wksp --help.

🏗 Role 2 — Architect
Architect

Structural changes — flag naming and grouping, command flow, what to remove vs. consolidate, and what the first-time mental model should look like.

Verb-first command redesign (v2.0)

Approved direction: put the verb first, like kubectl. The object (--task, --repo) is a flag, and list takes the noun as a subcommand. This makes every command readable as a sentence and makes tab-completion on the verb surface everything you can do.

Currentv2.0 Verb-FirstNotes
wksp task <id>wksp open <id>Primary workflow — open or create a task workspace
wksp task <id> --delwksp delete --task <id>Verb-first; wksp delete alone still deletes the project
wksp task <id> --archivewksp archive --task <id>Top-level action verb
wksp task <id> --unarchivewksp restore --task <id>"restore" is clearer than "unarchive"
wksp task <id> --rename <new>wksp rename --task <id> <new>Rename and exit — no Claude launch
wksp listwksp list taskstasks is default if no noun given
wksp repo listwksp list reposConsistent noun pattern
wksp repo <path>wksp add --repo <path/url>Verb-first add
wksp repo <path> --removewksp remove --repo <path>Symmetric with add

All v1.x commands stay as deprecated aliases in v2.0 with warnings. A migration script handles automatic config/script updates for users upgrading.

Make wksp repo a subcommand group

CommandReplaces
wksp repo list(new — currently requires opening repos.txt)
wksp repo add <path> [--shared] [--as <alias>]wksp repo <path>
wksp repo remove <path> [--as <alias>]wksp repo <path> --remove

wksp repo <path> with no subcommand stays as an alias for add for muscle memory. --remove is deprecated with a warning.

Overhaul wksp cleanup

CommandBehavior
wksp cleanupScan all repos registered in the current project (default, zero-arg)
wksp cleanup <path>Prune a specific directory
wksp cleanup <path> --recursiveScan first-level subdirectories

Kill --stale (mandatory option = bad design). Kill -r (only short flag in the tool). Keep both as deprecated aliases with warnings.

Rename the conversion flags

Old FlagNew FlagReason

--to-worktree <repo>--use-worktree <repo>Consistent with above
--to-exclude <repo>--exclude <repo>Drops the preposition, cleaner verb

The docs and help text should lead with these three in this order. Everything else is plumbing.

👤 Role 3 — UX Reviewer
UX Reviewer

Thinking like a developer who has never seen this tool. What would confuse them? What defaults would surprise them?

1
High   The branch prompt is the highest-friction moment and gets no preamble
▼

A new user runs wksp task PROJ-123 and immediately gets:

Branch for backend [Enter=current, name=new/existing, s=shared, x=exclude]:

Approved simplification: drop name=new/existing — it's redundant. Whatever the user types after the colon is the branch name; the label adds noise without adding meaning. The prompt becomes:

Branch for backend [Enter=current, s=shared, x=exclude]:
  s — use a shared worktree (all tasks share one checkout)
  x — exclude this repo from this task

The two-line hint only prints on the first wksp task run (tracked in config) or when --help is passed. There is no explanation of what "shared" or "exclude" mean in context — first-time users will press Enter for everything, which is correct, but they won't know why s and x exist or when to use them. The inline hint solves this without cluttering every invocation.

2
High   wksp list goes quiet about archived tasks Fix approved
▼

If PROJ-123 was archived and you run wksp list, you see nothing for it. No indication that anything exists in archived state. A user who archived a task would assume it's gone. The output footer should say: "2 archived task(s) — run wksp list --archived to see them."

3
High   reposRoot is jargon at the worst moment Fix approved
▼

During wksp init, if reposRoot is not set, the user is prompted for it. They are trying to create a project; they don't know what reposRoot means yet. The prompt needs plain-English context: "Directory where GitHub repos will be cloned. Only needed if you plan to register repos by GitHub URL — local paths don't need this."

4
Medium   wksp delete asks for y to delete everything
▼

The user typed wksp delete. They will type y without reading. Requiring them to type the project name (e.g. acme) ensures they read and confirm. The confirmTyped() function already exists in lib/prompts.js — this is a one-line change in delete.js.

5
Medium   wksp config get dumps raw JSON
▼

Developers expect formatted key-value output from a config command, not raw JSON. Ideally each key includes a short description of what it does. autoResume and reposRoot should be listed with their purpose even when unset.

reposRoot   /c/dev/repos        — directory for GitHub repo clones
autoResume  true                 — auto-resume last Claude session
6
Medium   .code-workspace file is generated silently
▼

The task command writes a VS Code multi-root workspace file to the project root. Nothing tells you this happened or where it is. A simple ✓ acme--PROJ-123.code-workspace (VS Code multi-root) line in the task creation output would make this discoverable.

7
Low   No wksp --version
▼

Every developer's first instinct when debugging is to check what version they have. Not having it is a broken expectation. Two lines in bin/wksp.js.

8
Low   "task" is the wrong word for the main command
▼

wksp task PROJ-123 sounds like task management software. The actual action is "open an isolated workspace for this ticket." wksp open PROJ-123 or wksp work PROJ-123 would communicate this better. That said, renaming the primary command is high-disruption — at minimum, every piece of help text should explain what "task" means in one sentence.

🗺️ Implementation Roadmap
Roadmap

Two-track plan: v1.x keeps the current surface but fixes friction and adds missing basics. v2.0 is a breaking major with verb-first redesign, new features, and removal of the --as alias. A migration script ships with v2.0 so users can upgrade safely or stay on v1.x.

Breaking change boundary: every rename in this document (flag renames, command restructure, verb-first syntax) is a breaking change and belongs in v2.0, not v1.x. v1.x only gets additive changes and bug fixes. v2.0 carries deprecated aliases for every changed command so the migration script can find and update them automatically.

Revert --as <alias> (PR #3)

🗑️
Decision: revert. Registering the same repo twice under different aliases is a workaround for a multi-branch workflow that should instead be handled at the task level. It adds complexity to parsing, listing, and worktree management without serving the common case. A workspace should be about distinct repos.
⚠️
Side-effect to track: PR #3 bundled more than just the --as flag — it also changed the default branch name behavior (e.g. from production to current). Reverting the PR wholesale will undo that change too. Before reverting, diff PR #3 carefully and cherry-pick out any behavior changes that should be kept. Decisions elsewhere in this document that reference branch naming may need to be revisited if that behavior reverts.

Revert PR #3 (feat: allow same repo registered twice via --as <alias>) before v2.0. Any users relying on it should use separate tasks with distinct repo registrations instead.

New Feature: Shared dependencies (node_modules / venv)

Problem: when a workspace has multiple tasks, each task clones its own node_modules (or Python venv) — usually identical. This wastes disk and slows task creation.

Options evaluated:

OptionProsCons
A. Symlink to original repo's node_modules Zero extra setup; always in sync with the main checkout Breaks if the task branch has different deps; can pollute the shared install if a task runs npm install
B. Shared cache dir in project root Isolated from the source repo; controlled by wksp; all tasks share one install Requires a "link" step on task creation; cache can drift from per-task lockfiles
C. Per-task install (current behavior, explicit opt-in) Maximum isolation; never wrong Slow and disk-heavy
💡
Recommendation: Option B as opt-in, with Option C as default. Add a sharedDeps: true config flag per repo registration. When enabled, wksp creates a .wksp-deps/<repo-name>/node_modules directory in the project root and symlinks each task's node_modules to it. The user runs wksp install --repo <name> once to populate it. Option A is too risky. Option C stays the default — the performance win only matters when tasks > 2 and repos are large.

Same pattern applies to Python venv: .wksp-deps/<repo-name>/.venv symlinked into each task. Worth it when a repo has a heavy venv (e.g. ML dependencies) used identically across all tasks.

New Feature: Workspace export/import with AI context Approved

Use case: share a workspace with a teammate who should continue working on it — including the Claude session context, task state, and repo configuration — without manual setup.

Export — always includes project info:

CommandWhat it bundles
wksp export --task <id> [--out <file>]Project config + repo list (with remote URLs) + the specified task's branch state and Claude session transcript. Always self-contained — no prior setup required on the receiving end.
wksp export [--out <file>]Full project: config, all repos, all tasks, all Claude contexts.

Import flow:

StepBehavior
1. Read manifestParse the bundle's project name, repos, and tasks
2. Choose modePrompt: "Create a new project from this export, or import into an existing project folder?"
3a. New projectCreate project directory, register repos (clone from remote URL or prompt for local path), restore tasks and AI context
3b. Existing projectDiff the export's project config against the current project: show a comparison table (repos present/missing/renamed, config key differences). User confirms before anything is written. Only the exported task and its context are added — existing tasks and config are untouched unless the user opts in.
4. Seed AI contextPlaces Claude session transcript in each restored task directory so wksp open <id> resumes from it
⚠️
Claude context portability caveat: Claude session transcripts are stored locally (not in any cloud). The export includes the raw transcript JSON. The teammate's wksp uses it as the initial context file on claude --continue. This works today with Claude Code's --resume flag. Verify the exact flag name before implementation.

Migration script (v1.x → v2.0)

Ships as wksp migrate (or npx wksp-migrate for users on v1.x who haven't upgraded yet).

StepWhat it does
1Detect v1.x project structure (presence of repos.txt, task folder layout)
2Scan shell scripts / package.json scripts for wksp task, wksp repo --remove, etc. and rewrite to v2.0 syntax
